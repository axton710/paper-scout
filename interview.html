一句话话术 / Elevator Pitch

它是一个 orchestrator-worker + pipeline + reflection 的多智能体系统：Planner / Searcher / Synthesizer / Gap / Verifier 各司其职、上下文隔离，各自通过 MCP 自主调用 AMiner 学术工具；协调层我刻意做成中心化的 Python 编排，用可控性、成本纪律与可复现换掉了去中心委派的不确定性。

01

动机 why multi-agent

◆ 单 agent 做文献调研的三堵墙

  • 漏：一个上下文塞十几篇，很快超窗、相互干扰，广度不够。
  • 浅：兼顾"铺开"与"挖深"，两头都做不好。
  • 不主动找 gap：综述式总结 ≠ 批判性地找没人做的点。

◆ 多 agent 恰好对症

  • 广度并行：每个子方向一个 Searcher，独立上下文。
  • 分工深挖：规划 / 检索 / 综述 / 找 gap 各是专职角色。
  • 找创新点 = 独立认知任务：Gap agent 专职，Verifier 核验。

三层职责

  • ① 编排层 · Python：决定跑谁、传递中间结果、成本记账。
  • ② 推理层 · dsh agent：每角色一次隔离调用，自主 tool-use。

为什么建在 dsh 上

  • 用真实开源 agent 框架，而非套壳 demo——能谈架构与取舍。
  • MCP 挂载：一段配置把外部数据源变成 agent 的原生工具。
  • 会话事件流天然可做成本与调用归因。
03

关键技术选型 decisions to defend

Integration

把 AMiner MCP 挂进 dsh，让 agent 自主调工具

streamable-http + Bearer 挂载托管 MCP，26 个学术工具以 mcp__aminer__* 进入工具表；agent 以 ReAct 方式自己决定搜什么、精读哪几篇。硬命中 JD 的 MCP / Tool Use。

Orchestration

代码编排 vs subagent 自主委派

工作流已知且固定，所以编排写进代码：换来确定性、成本可控、可缓存复现（重跑复用语料，AMiner 零调用）。开放式、分解不定、需递归深度时，才用 subagent 委派——两条路的代价都清楚。

Reflection & Cost

生成-核验-回改的反思闭环

创新点走真正的 Reflection 环：Gap 生成 → Verifier 严格判 keep/weak/drop → 把 weak/drop 连同理由喂回 Gap 收窄重出 → 再核验（≤2 轮）。实测 R1 keep4/weak2 → 回改 → R2，weak 被收窄成更具体的方向。成本侧：事件流记账 AMiner 调用 + token、精读接口设上限。

Robustness

让 LLM 稳定吐结构化数据

LLM 出 JSON 是工程难点：prompt 约束 + json-repair 兜底 + 列表归一三重保险；session id 唯一化防持久化冲突；综述预算调优（推理吃光输出预算导致正文为空的坑）。

06

面试追问预备 drill

为什么不用单 agent？
上下文隔离 + 并行铺开 + 分工找 gap——单 agent 会超窗、变浅、且不会主动找空白。这是多 agent 的硬收益，不是"为多而多"。
为什么不用 subagent 自主委派？
工作流已知固定，代码编排更可控、可缓存、成本卡死；检索接口计费，尤其看重这点。开放式、分解不定的任务我才会换成 subagent 委派——两种方案的边界我清楚。
怎么控成本 / 防幻觉？
记账 + 精读上限控成本；Gap 必须 grounded 到具体论文、Verifier 核验剔除假新颖——防"编方向"。
怎么评测 / 怎么终止？
固定流程 → 可复现、便于评测；Verifier 给 keep/weak/drop；子方向数 K 设上限、每方向精读上限，终止条件明确。
